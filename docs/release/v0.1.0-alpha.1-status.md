## Authority model

The root `[workspace.package].version` is the compile-time semantic-version authority. Every participating package inherits that value, and the CLI reads it through `CARGO_PKG_VERSION`; there is no writable Rust version string. The governed release manifest declares the expected version, the separate machine and display release tiers, the exact 14-package set, and expected formula-registry counts. `cargo run -p xtask -- verify-release-identity` compares those declarations with real Cargo metadata, discovered package manifests, the production registry parser, governed documents, and a compiled CLI process.

The release tier is not a formula validation status, execution policy, implementation status, or package version. The historical `beta1-concept` name is retained only in clearly scoped historical documentation and compatibility descriptions; it is not the runtime identity.

## Review corrections and fixture architecture

The Markdown scanner records the opening delimiter character, delimiter length, and source line. A close must use the same character, use a run at least as long, and contain only accepted trailing whitespace; unmatched fences fail closed. Non-authoritative fenced examples remain ignored, while prose after a matching close remains governed. HTML comment state is independent of fence state: outside fences, only bytes from `<!--` through the matching `-->` are hidden, visible prefixes and suffixes remain on their original physical lines, multiple and multiline comments are processed in order, stray closing markers are rejected, and end-of-file inside a comment fails closed. Comment markers inside a valid fence remain inert code content.

Historical treatment is limited to explicit historical blocks or grammatically separate historical clauses. A historical keyword, heading, `docs/beta1/` path, sentence, or clause never exempts a recognized assertion elsewhere in the paragraph. Each recognized assertion is parsed at its cue and bound to its immediately asserted semantic version, machine tier, display tier, program name, release channel, or runtime identity. Inline-code examples are masked as claim cues but remain accepted as the immediate value of an authoritative prose claim. Negation is recognized only for explicit forms equivalent to `VALUE is not the current release version`, `the current release tier is not VALUE`, or `does not claim VALUE as the current tier` (including the governed version/tier variants). Qualifiers such as `not merely`, `not only`, `not simply`, and double negatives do not suppress validation; unsupported polarity fails closed. A narrow negative clause exempts only its own proposition and never a separate affirmative assertion. Diagnostics include the file, starting and ending lines, claim type, asserted value, interpreted polarity, and expected value.

Governed documents reject UTF-8, UTF-16, and UTF-32 BOMs, `U+FEFF`, invalid UTF-8, `U+FFFD`, and prohibited mojibake while preserving valid scientific Unicode. Tests are classified accurately: 9 helper/unit functions cover narrow validators; 12 production-document functions call the governed scanner; 3 production-loader functions create real Cargo workspaces and checked registry JSON/SHA-256 pairs; 1 compiled-process function builds and executes drifted CLI binaries; and 1 complete public-command function runs 48 independently counted scenarios through `verify_release_identity` over a real cloned repository. That production-entry matrix covers LF, CRLF, permitted mixed endings, soft and hard wraps, historical/current separation, BOM and `U+FEFF`, HTML-comment boundaries, polarity, competing tokens, inline examples, identity-block integrity, and the discriminatory mixed-fence arrangement. A verifier-backed assertion keeps its scenario count synchronized with this evidence.
