## Authority model

Every participating package inherits that value, and the CLI reads it through `CARGO_PKG_VERSION`; there is no writable Rust version string. The governed release manifest declares the expected version, the separate machine and display release tiers, the exact 14-package set, and expected formula-registry counts. `cargo run -p xtask -- verify-release-identity` compares those declarations with real Cargo metadata, discovered package manifests, the production registry parser, governed documents, and a compiled CLI process.

The release tier is not a formula validation status, execution policy, implementation status, or package version. The historical `beta1-concept` name is retained only in clearly scoped historical documentation and compatibility descriptions; it is not the runtime identity.

## CI and threat-model boundary

Fresh GitHub Actions runners on Ubuntu, Windows, and macOS are the authoritative release-verification environments. Blocking CI covers formatting, Cargo metadata, workspace checks, Clippy, tests, documentation, checksums, the release manifest, release identity, generated artifacts, aggregate verification, dependency policy, CLI identity, formula counts, and self-check.

Pull-request jobs set `AEROCODEX_RELEASE_IDENTITY_REVISION` from the trusted `github.event.pull_request.head.sha` event value. The verifier resolves both checkout HEAD and that evaluated revision to full commit objects. Equal revisions use direct-checkout mode. A differing revision is accepted only as the second direct parent of a two-parent synthetic merge; the base parent, an older ancestor, an unrelated commit, a missing object, and a non-commit object fail closed. Push jobs supply `github.sha`, while ordinary local execution requires no environment variable and evaluates checkout HEAD. Fixed historical implementation commits are verified as ancestors of the evaluated revision. Commit subjects are not revision authority, so ordinary post-merge checkouts do not fail because their HEAD is a merge commit.

Local scripts are developer conveniences. They may require a clean checkout, but they are not an operating-system security boundary and do not claim to contain malicious build scripts. Adversarial build isolation is deferred to a later container, virtual-machine, or operating-system sandbox milestone.

Root `Cargo.lock` is absent from the committed Git tree. A pre-existing ignored `Cargo.lock` may exist physically in a local developer worktree; it is not part of the milestone's committed tree, and verification must not describe Git absence as literal physical absence. This corrective task preserves that file byte-for-byte and leaves it unstaged. The milestone does not decide the final release-binary lockfile policy: the packaging milestone will decide whether a root lockfile is committed. Removing a local ignored lockfile is cleanup outside this task and requires separate user authorization.

## Review corrections and fixture architecture

The Markdown scanner records one explicit, mutually exclusive parser state: `Visible`, `HtmlComment(opening_line)`, or `Fence(character, length, authority, opening_line)`. In visible state, a valid raw fence opener is recognized before HTML-comment parsing on that physical line. In fence state, every byte—including `<!--` and `-->`—is fenced content and cannot mutate comment state; only the same delimiter character, a run at least as long, and accepted trailing whitespace closes the fence. A shorter or mixed delimiter and a close-like line with trailing comment text remain fenced, and unmatched fences fail closed. After a true close the state is visible, so following prose is governed normally. Outside fences, only bytes from `<!--` through the matching `-->` are hidden, visible prefixes and suffixes retain their original physical lines, multiple and multiline comments are processed in order, stray closing markers are rejected, and end-of-file inside a comment fails closed.

Historical treatment is limited to explicit historical blocks or grammatically separate historical clauses. A historical keyword, heading, `docs/beta1/` path, sentence, or clause never exempts a recognized assertion elsewhere in the paragraph. Each recognized assertion is parsed at its cue and bound to its immediately asserted semantic version, machine tier, display tier, program name, release channel, or runtime identity. Inline-code examples are masked as claim cues but remain accepted as the immediate value of authoritative prose. Supported negative grammar is deliberately narrow: `VALUE is not the current release version`, `the current release tier is not VALUE`, or `does not claim VALUE as the current tier`, including the governed version/tier variants. The clause must contain exactly one `not` token owned by exactly one supported template. Multiple or nested negation, `not false`, `cannot`, `never`, `not merely`, `not only`, and other unsupported polarity fail closed. A supported negative exempts only its own proposition and never a later affirmative assertion. Ambiguous diagnostics include file, start/end lines, claim type, asserted value, expected value, interpreted polarity, and a machine-readable reason.

Governed documents reject UTF-8, UTF-16, and UTF-32 BOMs, `U+FEFF`, invalid UTF-8, `U+FFFD`, and prohibited mojibake while preserving valid scientific Unicode. Tests are classified accurately: 11 helper/unit functions cover narrow validators, the normalized-empty-commit fixture regression, and realistic direct/synthetic Git revision relationships; 12 production-document functions call the governed scanner; 3 production-loader functions create real Cargo workspaces and checked registry JSON/SHA-256 pairs; 1 compiled-process function builds and executes drifted CLI binaries; and 1 complete public-command function runs 55 uniquely named scenarios through `verify_release_identity` over a real cloned repository. The production-entry categories are 18 fence/comment, 18 polarity, 14 structure/encoding, and 5 immediate claim-binding scenarios. The matrix derives its runtime count, rejects duplicate names, and asserts that both the total and category counts match this release evidence; helper/unit or production-document tests are not described as end-to-end tests.
