## Contradictions recorded before resolution

1. The requested `v0.1.0-alpha.1` release identity conflicted with Cargo `0.0.1`, the human `Phase 0.001` label, and the `beta1-concept` CLI channel. This batch establishes a separate release-manifest version and does not change Cargo packaging metadata or CLI release identity.
2. README and `docs/beta1/cli_quickstart.md` described ten M00 formulas as an executable surface and showed a successful `research_required` run. The generated registry, status-gate policy, CLI gate implementation, and integration tests require all such runs to fail closed.
3. The CLI source held twelve dispatch specs (ten canonical-unit plus two angle conversions), while Beta 1 verification/docs claimed a supported count of ten. Dispatch linkage and self-check coverage are now distinguished from public executability; the release manifest records twelve linked records and zero public executable formulas.
4. `ARTIFACT_MANIFEST.md` called `checksums/SHA256SUMS` the current public file set, but the checksum manifest omitted 81 tracked files added after its last refresh and had 8 stale entries.
5. The documented `sha256sum -c checksums/SHA256SUMS` command was Unix-specific. On the inspected Windows checkout, Git `core.autocrlf=true` converted the checksum manifest and governed text files to CRLF, causing the raw tool to treat all 419 manifest paths as ending in `\r`; an independent canonical audit then found 408 line-ending-only matches, 8 real stale hashes, and 3 raw-byte matches.

## Independent-review remediation

The independent review was performed against commit `4bc8d954263831d80952187e650b713941cd0c80`. The worktree was clean at the start of remediation and the branch was one commit ahead of its upstream. The following baseline questions were resolved before code changes:

- `Cargo.lock` was absent from both the pinned base tree and the reviewed commit, so the reviewed commit did not delete a tracked lockfile. The root lockfile remains intentionally ignored and excluded under the current library-oriented workspace policy; this is not a new packaging decision.
- `python3.cmd` was neither tracked nor present in the workspace and did not appear in the reviewed commit. The earlier mention referred only to a temporary, external test-environment experiment.
- The earlier 26-file statistic was a provisional diff that omitted six then-untracked new files. The committed review surface was 32 files. This remediation also changes the previously unaffected CLI source and adds one structured dispatch metadata file, producing the 34-file cumulative list recorded below: 2,723 insertions and 267 deletions from `ffcc2b2`.

The four review findings were addressed without changing formula mathematics, validation status, execution authorization, release identity, packaging, or publication state:

1. CLI dispatch metadata is now a checked-in structured source consumed directly by the CLI and release verifier. The release manifest must exactly match its canonical formula IDs and runtime symbols; replaced, missing, extra, duplicate-ID, duplicate-symbol, and symbol-mismatch cases are covered by negative tests.
2. The pinned base revision must resolve to an actual Git commit and be an ancestor of `HEAD`. CI fetches full history, and malformed, nonexistent, non-commit, non-ancestor, and source-archive cases fail with explicit diagnostics.
3. Checksum verification now enforces exact set equality, rejects excluded and aliased paths, governs symbolic links, documents every exclusion, and limits CRLF normalization to an explicit text allowlist so binary content remains byte-exact.
4. Generated-artifact drift verification now compares exact Git-aware before/after state, including tracked staged and unstaged content, executable modes, symlink targets, and nonignored untracked paths. It reports whether the unchanged baseline was clean or dirty; ignored `target/` output remains outside the delta.

## Cumulative branch-review closure

A cumulative review of corrective commit `48a3509c2c1be6b5d78e3b3df8efda739462e76f` identified five remaining integrity gaps. This focused follow-up closes them without changing any formula, the 152 `research_required`/blocked statuses, release identity, packaging, signing, publication, or promotion state:

1. Regular files and symbolic links now use a shared, versioned object-kind and length-framed checksum identity. Unix link targets retain raw non-UTF-8 bytes; Windows link targets use a deterministic lossless encoding of native UTF-16. Links are not followed, canonicalized, or slash-normalized.
2. Every release evidence reference must be a normalized repository-relative regular file whose canonical path remains inside the canonical repository root. Absolute paths, parent traversal, missing paths, directories, final symlinks, and symlink escapes receive specific failures. Filesystem containment remains testable without `.git`; only base-object ancestry still requires Git history.
3. Generated-state snapshots reuse the lossless filesystem identity, detecting raw symlink creation, deletion, retargeting, and link/file replacement, including Unix non-UTF-8 targets.
4. Generated-state enumeration bypasses repository, info, and global ignore rules. All files beneath generator-owned paths are inspected; only the explicit build/transient policy outside those paths is excluded.
5. The local handoff creates an absent transient root `Cargo.lock` atomically, deletes only that proven-owned untracked/ignored regular path, verifies it after every step, and preserves/fails on tracked, preexisting untracked, modified, type-changed, or otherwise ambiguous states. A dedicated shell harness covers success, failure, interruption, and paths with spaces.
