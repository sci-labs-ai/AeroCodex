Fresh GitHub Actions runners on Ubuntu, Windows, and macOS are the authoritative release-verification environments. Blocking CI covers formatting, Cargo metadata, workspace checks, Clippy, tests, documentation, checksums, the release manifest, release identity, generated artifacts, aggregate verification, dependency policy, CLI identity, formula counts, and self-check.

Pull-request jobs set `AEROCODEX_RELEASE_IDENTITY_REVISION` from `github.event.pull_request.head.sha` and `AEROCODEX_RELEASE_IDENTITY_BASE_REVISION` from `github.event.pull_request.base.sha`; push jobs set the evaluated revision from `github.sha` and leave the pull-request base empty. The verifier requires each supplied full SHA to name an exact unpeeled commit object. Equal checkout and evaluated revisions use direct-checkout mode without requiring a base. Commit subjects remain non-authoritative, so ordinary post-merge checkouts use direct mode regardless of subject text.

Local scripts are developer conveniences. They may require a clean checkout, but they are not an operating-system security boundary and do not claim to contain malicious build scripts. Adversarial build isolation is deferred to a later container, virtual-machine, or operating-system sandbox milestone.

## Review corrections and fixture architecture

The Markdown scanner records one explicit, mutually exclusive parser state: `Visible`, `HtmlComment(opening_line)`, or `Fence(character, length, authority, opening_line)`. In visible state, a valid raw fence opener is recognized before HTML-comment parsing on that physical line. In fence state, every byte—including `<!--` and `-->`—is fenced content and cannot mutate comment state; only the same delimiter character, a run at least as long, and accepted trailing whitespace closes the fence. A shorter or mixed delimiter and a close-like line with trailing comment text remain fenced, and unmatched fences fail closed. After a true close the state is visible, so following prose is governed normally. Outside fences, only bytes from `<!--` through the matching `-->` are hidden, visible prefixes and suffixes retain their original physical lines, multiple and multiline comments are processed in order, stray closing markers are rejected, and end-of-file inside a comment fails closed.

Historical treatment is limited to explicit historical blocks or grammatically separate historical clauses. A historical keyword, heading, `docs/beta1/` path, sentence, or clause never exempts a recognized assertion elsewhere in the paragraph. Each recognized assertion is parsed at its cue and bound to its immediately asserted semantic version, machine tier, display tier, program name, release channel, or runtime identity. Inline-code examples are masked as claim cues but remain accepted as the immediate value of authoritative prose. Supported negative grammar is deliberately narrow: `VALUE is not the current release version`, `the current release tier is not VALUE`, or `does not claim VALUE as the current tier`, including the governed version/tier variants. The clause must contain exactly one `not` token owned by exactly one supported template. Multiple or nested negation, `not false`, `cannot`, `never`, `not merely`, `not only`, and other unsupported polarity fail closed. A supported negative exempts only its own proposition and never a later affirmative assertion.
